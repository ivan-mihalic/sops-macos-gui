# UI/UX review of the main window — 2026-08-10

Driven against the **running app**, not against source or snapshots, using
`Scripts/ui-probe.swift` (Accessibility API, `open -g`, never activates the
app). Every number below was measured; none was reasoned about.

## Why the existing tools could not find any of this

`Scripts/snapshots.sh` renders views into an offscreen host at a size the
catalog chooses. There is no window, no title bar, no resize handle, no minimum
size and no run loop — so nothing about resizing, window limits, hit areas or
main-thread blocking is observable through it. Two releases "fixed" the window
size with source-reading tests that passed while the app stayed broken.

## Findings

| # | Finding | Evidence | Status |
|---|---|---|---|
| 1 | **The app hangs permanently when the Settings row is clicked.** `KeyImportView.init` runs the login shell; `Process.waitUntilExit()` spins a **nested run loop**, which re-enters AppKit's display cycle, which lays out the view still inside its own `init`, which spawns the process again. No bottom. | `sample(1)`: `NSHostingView.layout()` → … → `waitUntilExit` → `_CFRunLoopRun` → `NSDisplayCycleFlush` → `layoutIfNeeded` → `NSHostingView.layout()`. Window stayed on screen; every AX query returned `kAXErrorCannotComplete`. | **fixed** — `CommandRunner` waits without pumping a run loop. `MainThreadReentrancyTests` counts run-loop activity during a command and fails if any occurs. |
| 2 | **Window minimum width was 2177 pt** — it could not be narrowed at all. Three `NavigationSplitView`s nested inside one another, each contributing a sidebar, a toggle and a minimum. | `limits 0` → `min: 2177x224`. AX tree showed two elements named "Sidebar" and two toggle buttons. | **fixed** — `ProjectWorkspaceView` is one `HSplitView` inside the app's single `NavigationSplitView`. Minimum fell to 1138. |
| 3 | **Window limits changed with the selected pane** — Projects `min 1138x189`, About `min 352x1353`, Settings `min 270x179`. On Projects it would not narrow, on About it would not shorten. This is the reported "some screens resize and some don't". | `limits 0` per pane, twice each, with settle time. | **fixed** — constant across all panes. |
| 4 | **About broke the layout.** The split group stayed **1301 pt tall inside a 612 pt window** and hung off the top edge; the sidebar rendered empty. Caused by the sidebar's `safeAreaInset` refusing to compress. | `tree 0 3` → `AXSplitGroup 1140x1301@1090,230` while `AXWindow 1140x612@1090,549`. | **fixed** — sidebar is one `List` with two sections; content now tracks the window exactly on every pane. |
| 5 | **Sidebar rows were clickable only on their text.** `AXButton "About" 58x16` and `"Settings" 73x16` inside a 220 pt sidebar, next to a real `List` row that took a click anywhere. `.buttonStyle(.plain)` does not make padding hittable. | `tree 0 9`. | **fixed** — all three rows are `AXRow 220x32`. |
| 6 | **`.defaultSize` never applied.** SwiftUI restores its own frame on the run-loop turn *after* `onAppear`, so window configuration done there is silently undone. | Instrumented: `afterSetFrame=1180x760` → `nextRunLoopTurn=1600x1000`. | **fixed** — frame decision deferred past the restore, with one bounded retry. |
| 7 | **Saved frames of 2177x450 / 2177x1353** carried over from 0.1.0–0.1.2, indistinguishable from a deliberate size. | `defaults read cz.mihalic.SopsGUI`. | **fixed** — one-time reset keyed on `window.frameResetGeneration`; a size the user chooses afterwards survives relaunch (verified: 1500x900 → quit → 1500x900). |
| 8 | **Settings window (⌘,) and the onboarding sheet were fixed-size slabs** (`620x480`, `640x520`). | Source; sheet measured `AXSheet 560x560`. | **fixed** — both take a minimum and an ideal instead. |
| 9 | About showed an SF Symbol where the app icon belongs. | — | **fixed** — `NSApplication.applicationIconImage`. |

## Known and unfixed

- **Effective minimum is 1138 x 189.** 1138 is honest: `HSplitView` will not
  compress the three panes below it. 189 is permissive — the layout tracks the
  window down to it without overflowing, it is just cramped. `window.minSize`
  was tried both early and deferred; SwiftUI re-imposes its content-derived
  floor continuously and wins.
- **The structural fix for both is a single three-column
  `NavigationSplitView`**, which collapses columns as the window narrows —
  what Apple's own three-pane apps do. It needs the outer sidebar and the
  project list merged into one column, which changes the selection model and
  the unsaved-changes guard, so it is recorded rather than half-done.
- Section headers in the sidebar render as zero-height rows (`AXRow 220x0`).
  Harmless; they are the grouping separators.

## Not reviewed

The project → file list → editor flow was not walked with a real project: the
app has none configured and "Add Project…" opens an `NSOpenPanel`, which this
harness cannot drive. Seeding `ProjectStore` directly is the way in; not done
here.
