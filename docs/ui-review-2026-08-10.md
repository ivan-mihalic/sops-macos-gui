# UI/UX review of the main window — 2026-08-10

Driven against the **running app**, not against source or snapshots, using
`Scripts/ui-probe.swift` (Accessibility API, `open -g`, never activates the
app). Every number below was measured; none was reasoned about.

## Why the existing tools could not find any of this

`Scripts/snapshots.sh` renders views into an offscreen host at a size the
catalog chooses. There is no window, no title bar, no resize handle, no minimum
size and no run loop — so nothing about resizing, window limits, hit areas or
main-thread blocking is observable through it. Two releases "fixed" the window
size with source-reading tests that passed while the app stayed broken.

## Known and unfixed

- **Effective minimum is 1138 x 189.** 1138 is honest: `HSplitView` will not
  compress the three panes below it. 189 is permissive — the layout tracks the
  window down to it without overflowing, it is just cramped. `window.minSize`
  was tried both early and deferred; SwiftUI re-imposes its content-derived
  floor continuously and wins.
- **The structural fix for both is a single three-column
  `NavigationSplitView`**, which collapses columns as the window narrows —
  what Apple's own three-pane apps do. It needs the outer sidebar and the
  project list merged into one column, which changes the selection model and
  the unsaved-changes guard, so it is recorded rather than half-done.
- Section headers in the sidebar render as zero-height rows (`AXRow 220x0`).
  Harmless; they are the grouping separators.

## Second pass — the project → file list → editor flow

`NSOpenPanel` cannot be driven by this harness, so the flow was reached by
seeding `ProjectStore`'s JSON directly with a throwaway project holding two
real sops+age encrypted YAML files, and by adding a `selectrow` command to the
probe (`AXPress` on a row's text does nothing; a row is selected by setting
`AXSelected`).

Walked: project list → file list (both encrypted files listed) → editor. The
editor correctly refuses to open the file and says why — "Add your age private
key in Settings › Key" — rather than showing an empty form.

Resize was measured at each stage. With the editor open: `min 1138x316`, and
the content tracked the window exactly at 1140, 1400 and 1800 pt. No overflow
anywhere in the flow.

| # | Finding | Before | After |
|---|---|---|---|
| 10 | "Add Project…" clickable only on its text, inside a full-width sidebar footer | `AXButton 101x16` | `180x32` |
| 11 | The remove-key button was **eleven points tall** — a `minus` glyph is a short bar and the button shrank to it | `AXButton 37x11` | `44x28` |
| 12 | The add-key button beside it was a different size again | `AXButton 37x20` | `44x28` |

All three are the same defect as finding 5: a `.plain`-style button's hit
region is what it draws, and padding draws nothing. `ClickTargetTests` pins the
Add Project case — it reproduces the measured 101 pt when the fix is reverted.

## Third pass — the editor with a document, and dark mode

**Getting a key into the live app failed, and that is itself a finding about
the harness rather than about the app.** `AXValue` written to the key-import
`TextEditor` lands in the underlying `NSTextView` without going through its
editing path, so the SwiftUI binding never updates — measured: the field read
back 0 characters and the Import button stayed disabled. Replacing the
selection through `AXSelectedText` did not stick either. Typing with `CGEvent`
would work but needs the app focused, which this harness exists not to do.
Pointing `SOPS_AGE_KEY_FILE` at a fixture so the legacy-file import would offer
it did not reach the login-shell probe either.

So the editor **with a decrypted document** was reviewed by rendering, not by
driving — which is the right tool for the question anyway: window behaviour
with the editor present was already measured live (`min 1138x316`, content
tracked the window at 1140/1400/1800), and what remained was layout under
width, which is exactly what a render answers.

|---|---|---|---|
| 13 | **Row action buttons were clipped or missing at narrow widths.** At 320 pt — the editor pane's own declared minimum — the copy button was sliced by the pane edge. At 380 pt it was **absent from some rows and present on others**, depending on how long that row's key was. The value field (`minWidth: 160`) and the buttons competed for the same space and the field won. | `editor-loaded-narrow`, `editor-w380`, `editor-w440` | **fixed** — the pair is laid out at a reserved size and the field yields (`minWidth: 100`). Dark mode was swept for the first time beyond `AppShell`: `about-dark`,
`settings-pane-dark`, `editor-loaded-dark` are in the catalog and read
correctly — no invisible text, no light-mode surface showing through.

## Known and unfixed (continued)

- **The value column's left edge is ragged**: the key column is sized to
  content, so each row's field starts wherever that row's key ended. Visible in
  `editor-loaded-dark`. A `Grid` would align it; the cost is that one long key
  (`service.<<.timeout_seconds`) then sets the column width for every row.
- **Increased Contrast** was not swept.
