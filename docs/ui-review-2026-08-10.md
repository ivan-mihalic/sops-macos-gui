# UI/UX review of the main window — 2026-08-10

Driven against the **running app**, not against source or snapshots, using
`Scripts/ui-probe.swift` (Accessibility API, `open -g`, never activates the
app). Every number below was measured; none was reasoned about.

## Why the existing tools could not find any of this

`Scripts/snapshots.sh` renders views into an offscreen host at a size the
catalog chooses. There is no window, no title bar, no resize handle, no minimum
size and no run loop — so nothing about resizing, window limits, hit areas or
main-thread blocking is observable through it. Two releases "fixed" the window
size with source-reading tests that passed while the app stayed broken.

## Known and unfixed

- **Effective minimum is 1138 x 189.** 1138 is honest: `HSplitView` will not
  compress the three panes below it. 189 is permissive — the layout tracks the
  window down to it without overflowing, it is just cramped. `window.minSize`
  was tried both early and deferred; SwiftUI re-imposes its content-derived
  floor continuously and wins.
- **The structural fix for both is a single three-column
  `NavigationSplitView`** — planned in detail in
  `docs/plans/three-column-navigation.md`, not started, which collapses columns as the window narrows —
  what Apple's own three-pane apps do. It needs the outer sidebar and the
  project list merged into one column, which changes the selection model and
  the unsaved-changes guard, so it is recorded rather than half-done.
- Section headers in the sidebar render as zero-height rows (`AXRow 220x0`).
  Harmless; they are the grouping separators.

## Second pass — the project → file list → editor flow

`NSOpenPanel` cannot be driven by this harness, so the flow was reached by
seeding `ProjectStore`'s JSON directly with a throwaway project holding two
real sops+age encrypted YAML files, and by adding a `selectrow` command to the
probe (`AXPress` on a row's text does nothing; a row is selected by setting
`AXSelected`).

Walked: project list → file list (both encrypted files listed) → editor. The
editor correctly refuses to open the file and says why — "Add your age private
key in Settings › Key" — rather than showing an empty form.

Resize was measured at each stage. With the editor open: `min 1138x316`, and
the content tracked the window exactly at 1140, 1400 and 1800 pt. No overflow
anywhere in the flow.

| # | Finding | Before | After |
|---|---|---|---|
| 10 | "Add Project…" clickable only on its text, inside a full-width sidebar footer | `AXButton 101x16` | `180x32` |
| 11 | The remove-key button was **eleven points tall** — a `minus` glyph is a short bar and the button shrank to it | `AXButton 37x11` | `44x28` |
| 12 | The add-key button beside it was a different size again | `AXButton 37x20` | `44x28` |

All three are the same defect as finding 5: a `.plain`-style button's hit
region is what it draws, and padding draws nothing. `ClickTargetTests` pins the
Add Project case — it reproduces the measured 101 pt when the fix is reverted.

## Third pass — the editor with a document, and dark mode

**Getting a key into the live app failed, and that is itself a finding about
the harness rather than about the app.** `AXValue` written to the key-import
`TextEditor` lands in the underlying `NSTextView` without going through its
editing path, so the SwiftUI binding never updates — measured: the field read
back 0 characters and the Import button stayed disabled. Replacing the
selection through `AXSelectedText` did not stick either. Typing with `CGEvent`
would work but needs the app focused, which this harness exists not to do.
Pointing `SOPS_AGE_KEY_FILE` at a fixture so the legacy-file import would offer
it did not reach the login-shell probe either.

So the editor **with a decrypted document** was reviewed by rendering, not by
driving — which is the right tool for the question anyway: window behaviour
with the editor present was already measured live (`min 1138x316`, content
tracked the window at 1140/1400/1800), and what remained was layout under
width, which is exactly what a render answers.

| # | Finding | Evidence | Status |
|---|---|---|---|
| 13 | **Row action buttons were clipped or missing at narrow widths.** At 320 pt — the editor pane's own declared minimum — the copy button was sliced by the pane edge. At 380 pt it was **absent from some rows and present on others**, depending on how long that row's key was. The value field (`minWidth: 160`) and the buttons competed for the same space and the field won. | `editor-loaded-narrow`, `editor-w380`, `editor-w440` | **fixed** — the pair is laid out at a reserved size and the field yields (`minWidth: 100`). Verified at 320: both buttons present on every row, and now aligned in a column instead of ending wherever each row's field did. |

Dark mode was swept for the first time beyond `AppShell`: `about-dark`,
`settings-pane-dark`, `editor-loaded-dark` are in the catalog and read
correctly — no invisible text, no light-mode surface showing through.

## Fourth pass — the three-column attempt, and what it uncovered

The three-column `NavigationSplitView` from `docs/plans/three-column-navigation.md`
was implemented in the shape that needs **no guard changes at all**: sections in
`sidebar`, the project list in `content`, files + editor in `detail`. All 714
tests stayed green, including the six files that pin the unsaved-changes guard.

Measured: **Projects' minimum width fell 1138 → 910.** Then About came back at
`min 569x1382`, and the window grew to match.

Reverting the restructure did **not** restore About — it measured `388x1382`
against 0.1.5's own code. So the three-column change had not caused it; it was
already shipped, and the earlier "constant across panes" reading was taken at a
moment when it did not show. That is the second time `limits` (which jumps
straight to 1x1) has given a reading a gradual drag does not reproduce, and it
is why the finding below was measured by shrinking in steps instead.

| # | Finding | Evidence | Status |
|---|---|---|---|
| 14 | **The About row grew the window to 1382 pt and then would not let it shrink** — any width, gradually or in one jump. Live in 0.1.5. | Graded shrink: 900 → 760 → 700 → 640 → 600 → 560 all returned `1180x1382`. Substituting a plain `Text` in the detail column let the same window go to 700 immediately. `AboutView`'s own `fittingSize` is 358 pt, so no isolated render predicts it. The app icon and the frame modifiers were each ruled out by measurement first. | **fixed** — the page is in a `ScrollView`, which proposes no minimum height. All three panes now shrink to 1180x560. |

**The three-column restructure was reverted, then re-attempted against the
fixed baseline — and kept.** Measured by stepping down, on each pane:

| pane | before (two columns) | after (three columns) |
|---|---|---|
| Projects | `min 1138` wide | **`910x500`** |
| About | pinned at `1382` tall | **`700x500`** |
| Settings | — | **`700x500`** |

Content tracks the window exactly on all three. Sections in `sidebar`, the
project list in `content`, files + editor in `detail` — the shape Apple's own
three-pane apps use, with column collapsing that `HSplitView` cannot do.

It needed **no change to the unsaved-changes guard**, and that is the reason it
was safe: `ProjectSidebar` still writes `projects.selection` and
`ProjectWorkspaceView` still observes it through `requestProjectSwitch`. Which
column a view sits in does not change who asks before discarding a document.
`ThreeColumnGuardWiringTests` pins both halves, and reddens when either is cut.

## Known and unfixed (continued)

- **The value column's left edge is ragged, and this is now a decision rather
  than an oversight.** The key column is sized to its own content, so each
  row's field starts where that row's key ended (visible in
  `editor-loaded-dark`). Aligning it needs a fixed key column, and at the
  editor pane's 320 pt minimum the arithmetic does not leave room: the value
  field needs 100 and the two controls 48, so the key column can be at most
  ~150 there — narrower than most of the keys this app shows. A fixed width
  wide enough to be useful overflows the minimum; one narrow enough to fit
  truncates every key on every row, at every window size, to suit the
  narrowest. `Grid` does not help, because a `List`'s rows are separate views
  and share no grid. Content-sized keys keep the most key text readable, which
  is what a user identifying a secret is actually reading.
- **Increased Contrast cannot be rendered by this catalog, and the attempt is
  recorded rather than faked.** `NSAppearance(named: .accessibilityHighContrastAqua)`
  resolves and can be assigned to the hosting view, and the resulting PNG came
  out **byte-identical** to the ordinary one (`cmp`). SwiftUI derives
  `\.colorSchemeContrast` from the *system* setting
  (`NSWorkspace.accessibilityDisplayShouldIncreaseContrast`), not from a view's
  appearance, and this app draws with SwiftUI colours rather than AppKit
  chrome. The plumbing was removed; a catalog of images claiming an appearance
  they were not rendered in is worse than an admitted gap. Checking it for real
  means turning the system setting on, which is the machine owner's to do.

  What that setting exists to protect **is** now asserted, and directly:
  `ColourIndependenceTests` checks that no two health statuses share a glyph
  and no two share their words, so meaning never rests on tint alone — the same
  requirement Apple's guidance states, and the one a colour-vision deficiency
  or a monochrome display depends on just as much as Increased Contrast does.
  The first version of that test read the rendered accessibility tree and was
  **useless**: SwiftUI does not publish an SF Symbol's name as a label, so
  giving `.warning` and `.problem` the same glyph left it green. It now asserts
  the mapping, and the same mutation reddens it.

- ~~**The live editor with a decrypted document could not be reached**~~
  **— reached, on the fourth attempt.** The `Menu` *does* open under `AXPress`;
  the earlier failure was that the probe pressed it and then looked for the
  item in a *second process invocation*, by which time the menu had closed.
  Doing both in one process works. Walked live with a throwaway age key and two
  real encrypted files:

  - the editor shows the decrypted rows (`db_password`, `api_token`, `endpoint`)
  - values reach the accessibility tree **masked** (`AXTextField "••••••••"`),
    not in the clear — the never-log rule holds on that channel too
  - Reveal and Copy are `20x20` and aligned at the same x on every row, which
    is finding 13's fix confirmed on a real document rather than a fixture
  - resize with the document open: `min 1138x205`, content tracked the window
    exactly at 1140 / 1300 / 1700 / 2100 pt, and all six row controls stayed
    visible down to the minimum

  Kept for the record, because the three dead ends are worth not repeating:
  1. `AXValue` written to the key-import `TextEditor` lands in the underlying
     `NSTextView` outside its editing path — the field read back 0 characters
     and Import stayed disabled.
  2. Replacing the selection via `AXSelectedText` did not stick either.
  3. The legacy key-file route renders a SwiftUI `Menu` when more than one
     candidate exists, and `AXPress` on an `AXMenuButton` does not open it
     without the app being active. Narrowing it to the single-candidate case
     (which is a plain `Button`, and does respond) needs
     `~/.config/sops/age/keys.txt` not to exist; `NSHomeDirectory()` ignores a
     `HOME` override for a non-sandboxed app, so it cannot be arranged without
     touching the machine owner's real key file.

  `CGEvent` typing would have needed focus, which is the one thing this harness
  exists not to take. The route that worked needed none of it.
